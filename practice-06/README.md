# Практическая работа № 6

Подключение браузерного приложения к API.

**Автор** — Узеев Руслан, ЭФБО-05-25, вариант 5. Окружение — Node.js 24.16.0, npm 11.13.0.

## Запуск

Из корня проекта:

```bash
npm --prefix practice-06 start
npm --prefix practice-06 test
```

Первую команду оставить в отдельном терминале. Открыть [приложение](http://127.0.0.1:5506/), [вариант 5](http://127.0.0.1:5506/?dataset=variant) или [браузерные проверки](http://127.0.0.1:5506/checks.html). API слушает http://127.0.0.1:5505/api. Настольное открытие через `file://` не требуется. Сервер ПР5 использует тот же порт API, поэтому перед запуском ПР6 его нужно остановить.

## Реализация

- `api-client.js` формирует запросы GET, POST, PATCH и DELETE, добавляет JSON-заголовки, проверяет ответы и различает HTTP-ошибку, сетевой отказ, некорректный ответ, тайм-аут и отмену.
- `task-api.js` отвечает за маршруты, параметры, проверку коллекций и отдельных задач. При создании id и начальный статус определяет сервер.
- `app-controller.js` управляет состоянием `loading → ready | empty | error`. При ошибке исходной загрузки повтор снова запрашивает категории и список. После каждой мутации выполняется GET с текущими фильтрами. Кнопки изменения блокируются до завершения операции.
- Каждая новая загрузка отменяет предыдущую и получает собственный номер. Даже если предыдущий результат после отмены всё же получен, он не меняет представление.
- `form-validation.js` проверяет название, приоритет и категорию. `task-view.js` обновляет карточки через `replaceChildren`, а значения сервера выводит через `textContent`. Обработчики и DOM собраны в `dom-app.js`.

## Индивидуальный сценарий

При открытии `/?dataset=variant` начальный запрос `GET /api/tasks?categoryId=1` вернул id 1, 7, 13. У задачи №1 «Изучить функции» категорию «Учёба» сменили на «Проект» и сохранили. Ожидалось, что повторный GET с фильтром категории 1 вернёт id 7 и 13. Браузер показал «Изменения сохранены» и оставил в списке две задачи, №7 и №13.

## Ответы на контрольные вопросы

1. Статусы 404 и 500 означают, что HTTP-ответ получен. Поэтому `fetch` возвращает `Response`, а код проверяет `ok`.
2. Сначала проверяется `ok`, затем 204, тип содержимого и разбор JSON.
3. POST создаёт запись с назначенным сервером id. PATCH изменяет только переданные поля существующей записи.
4. 201 подтверждает создание ресурса. `Location` даёт адрес созданного ресурса.
5. У 204 нет тела, поэтому парсер JSON вернул бы ошибку.
6. Браузер отправляет OPTIONS для межсайтового запроса, который выходит за рамки простого, например для PATCH или JSON POST. `no-cors` ограничивает методы и не даёт прочитать ответ.
7. При `empty` сервер успешно вернул пустую выборку. При `error` для текущего запроса нет подтверждённых данных.
8. Сервер владеет актуальным набором, id и результатом изменений. Локальное хранилище не синхронизирует эти сведения.
9. Мутация может изменить принадлежность задачи к выборке. Повторный GET применяет текущий фильтр на сервере.
10. Первый запрос может закончиться позже второго и перезаписать его результат.
11. Ответ может быть уже получен или тестовый клиент может игнорировать сигнал. Номер загрузки позволяет отбросить устаревший результат.
12. Отменённый запрос обычно вытеснен новым. Пользователь ждёт результат нового запроса.
13. Клиент проверяет форму для быстрой обратной связи. Сервер повторяет проверку и контролирует правила данных, поскольку запрос можно отправить напрямую.
14. Переданный `view` позволяет проверять контроллер без DOM.
15. `textContent` отображает строки как текст и не исполняет HTML из ответа.
